4. Attempts and reported outcomes
==============================================================================

Attempt A — Diagnose the packaged single-lane script
What: Packaged swirling_vortex.lua used get_group("32 Ordered") and a hardcoded
      32-name fallback. Anyone not in that list started Lua and immediately
      returned. Catalog described a single 3-yalm lane. LuaTrajectoryController
      forced walk/run from speed, computed LuaTrajectoryFollower, then ignored
      it and steered at a raw world sample. FaceDirection via AutoFace ran
      constantly (jitter).
Outcome: Explains missing people, one ring, stacking on r=3 with 32 people,
         cohesion loss, jitter. Not yet a playable two-ring vortex.

Attempt B — Two rings from gait + slot/count + follower steering
What: Script used mop.get_slot()/get_count(), walk inner / run outer, auto
      radius from count and walk/run pace (outer could grow to ~10 yalms).
      Controller preserved walk/run, used follower LookAheadTarget, relative
      movement, rate-limited tangent facing. Built Debug only at first.
Outcome: Dalamud did not reload (watches Release). After
      Build-HotReload.ps1 -Deploy, live test continued.

Attempt C — User: circle too large walking and running; they bunch; want
          equal distance between neighbors. Then "stop".
What: Work stopped. No further size/spacing change in that turn.
Outcome: Large radii and bunching still present.

Attempt D — "Not necessarily 32. Needs to know who is online." Then
          "is_visible from the roster."
What: Agreed is_visible = roster member currently in this client's object
      table, not merely saved in the formation. Added is_visible on
      participant snapshots. Script compacted visible members every loop and
      used smaller radii (inner 1.50, outer 2.20).
Outcome: See Attempt E.

Attempt E — User: deforms when the target moves; should be laser-focused;
          looks like a semicircle; members not equally spaced.
What: Two causes:
      1) Fallback or uncompacted 32-slot phases put consecutive visible
         people on half the ring (semicircle).
      2) Movement only applied on new Lua samples (30 Hz) using a stale
         anchor, so the ring chased a ghost and packed behind the target.
      Fix: live anchor + offset every framework tick; compact visible;
      stop using follower look-ahead as the MoveTo destination.
Outcome: See Attempt F.

Attempt F — User: walk mode, two groups on top of each other. Target moves:
          scatter and deform. Run mode: not cohesive, constantly mutating.
          Target moves: scatter and reform.
What: Root causes:
      1) Each PC compacted locally. PC1 slot 0 and PC2 slot 0 were the same
         world point -> two bands stacked.
      2) Visibility and is_walking were re-read every tick. Object-table
         flicker changed n, phases, and inner/outer radius -> mutating ring.
      3) Rate-limited facing toward a chasing slot peeled people off, then
         they reformed when the target stopped.
      Fix: conductor freezes visible CID list at launch and sends it to every
      client; freeze slot/count/gait/radius in Lua; larger outer ring (2.80);
      0.16s translation lead; immediate facing when far from slot.
Outcome: Latest live report: facing is wrong when run mode is on.
      Cohesion/stacking/moving-target after this deploy were not separately
      re-confirmed in this session.

Attempt G — Current facing path (the open bug)
What: MoveTo is called with faceDirection: null. FormationNaturalMovement
      therefore faces the tracking point (the slot), i.e. a chord toward the
      next point on the circle, not the tangent Lua already computed
      (math.atan(nx-x, nz-z)). In run mode that chord points more inward
      because the slot is farther ahead per second, so wrong facing is more
      obvious. Walk mode is slower so the chord is closer to the tangent.
Outcome: Reported: facing direction is wrong when run mode is on.
      Not implemented. Stopped here.
